## 이 글에서는

제가 현재 다니는 회사에서 웹뷰를 처음 다뤄본 이후로 만났던 문제를 공유해보려고 합니다. 먼저 웹뷰에 대해 적고 제가 겪은 문제와 그 해결 방법에 대해 정리합니다. 그리고 모바일 브라우저에서의 문제도 조금 다룹니다. 기술 스택은 Next.js와 Flutter입니다.

먼저 고백하자면 이 글에서 소개하는 문제 해결 방법은 최선이 아닐 가능성이 다분합니다. 저는 단순하면서도 더 좋은 방법이 있을 것이라고 기대하고 있습니다. 그럼에도 불구하고 적어도 제가 아는 사실과 경험을 되짚어 보고자 기록을 남깁니다. 

## 웹뷰란?

웹뷰는 앱 화면 안에서 웹 페이지 렌더링하는 컴포넌트입니다. 그렇다면 모바일 브라우저도 앱의 일종이니까 웹뷰를 사용하고 있을까요? 모바일 크롬이나 사파리는 각각 Chromium과 WebKit을 사용하고 웹뷰를 사용하지는 않습니다. 다만, iOS는 정책상 서드파티 브라우저에게 WebKit 사용을 강제하고(17.4부터 EU만 예외), 그래서 iOS 크롬은 WKWebView로 웹 콘텐츠를 그립니다. 따라서 웹뷰를 사용하는 모바일 브라우저 앱도 존재한다고 할 수 있겠습니다.

앱은 웹뷰에서 자바스크립트를 실행시키고 네트워크 요청을 가로챌 수 있습니다. 이는 웹뷰와 브라우저를 가르는 기준이 되기도 합니다. 네이티브 코드와 메시지를 주고받을 수도 있죠. 한편, 브라우저로 열면 주소를 넘기는 것으로 끝입니다.

시스템 웹뷰로는 안드로이드의 android.webkit.WebView와 애플의 WKWebView가 있습니다. 전자는 패키지명과 달리 Chromium 기반입니다. 웹뷰는 같은 엔진의 브라우저가 제공하는 기능을 대부분 지원하지만 전부는 아닙니다. 예를 들어, 웹 푸시와 PWA 설치는 지원하지 않고 따라서 MDN에서도 WebView Android와 WebView on iOS를 별도 열로 표시합니다. 하지만 반대로 브라우저 환경과 다르게 동작을 제어할 수도 있습니다. 대표적으로 웹뷰 설정에 따라 사용자 제스처 없이 미디어의 자동 재생을 차단하는 정책을 비활성화시킬 수도 있습니다.

Custom Tabs와 SFSafariViewController는 웹뷰가 아닙니다. 이 구성들은 앱 안에서 호출할 수 있지만, 브라우저와 세션을 공유하는 별도 프로세스입니다. 즉, 앱이 페이지 내부에 개입할 수 없습니다.

앱 개발 환경에서 웹뷰를 제공하는 여러 수단이 존재합니다. 이 글에서 다루게 될 Flutter에서는 webview_flutter(공식)나 flutter_inappwebview(서드파티) 패키지로 시스템 웹뷰를 사용할 수 있습니다.

토스, 당근 등 국내 서비스도 화면 단위로 네이티브와 웹뷰를 나눠 씁니다.

## 웹뷰를 왜 쓸까?

웹뷰를 주요 스택으로 정하는 가장 큰 이유는 배포입니다. 자바스크립트로 만든 하나의 애플리케이션을 브라우저와 모바일 앱에 함께 올릴 수 있고, 네이티브 코드를 건드리지 않는 변경이라면 앱 심사를 기다리지 않고 갱신하거나 되돌릴 수 있습니다.

무심사 배포는 React Native 같은 프레임워크도 부분적으로 제공하지만, 같은 코드로 만든 화면을 공유하는 것은 웹뷰만의 특징입니다. 물론 웹뷰를 얹을 정도의 앱 개발은 필요합니다. 홍보 페이지나 링크 모음에 가까운 앱이라면 심사를 통과하지 못할 수도 있습니다. 그럼에도 앱 개발자를 따로 채용하지 않고 소수만으로 여러 플랫폼에서 동작하는 제품을 찍어낼 수 있다는 점은 분명한 이득입니다.

다만 어떤 비용이 줄어드는지는 구분해서 볼 필요가 있습니다. 일부 구현을 줄일 수 있습니다. 화면을 세 번 만드는 것을 한 번으로 줄일 수 있습니다. 이 절감 효과는 시간이 갈수록 누적됩니다. 플랫폼 사이의 스펙을 맞추던 조정 비용 및 심사를 기다리는 시간도 감소합니다.

반면 검증 비용은 줄어들지 않습니다. 만들 곳이 하나로 줄었을 뿐, 그 코드는 여러 플랫폼에서 동작합니다. iOS 앱과 안드로이드 앱, 두 OS의 브라우저, 그리고 태블릿까지. 오히려 네이티브라면 없었을 비용이 늘어납니다. WKWebView와 사파리의 동작 차이, 기기마다 다른 안드로이드 웹뷰 버전, 그리고 브릿지의 하위 호환 등을 챙겨야 합니다. 네이티브로 나눠 개발하면 iOS 개발자가 iOS를, 안드로이드 개발자가 안드로이드를 확인합니다. 하지만 웹 개발자 한 명이 iOS 앱과 안드로이드 앱, 크롬과 사파리를 모두 봐야 한다면 총량은 그대로인 채 한 사람 몫이 됩니다. Playwright나 BrowserStack으로 일부는 자동화할 수 있지만 실기기에서만 재현되는 문제는 결국 사람이 확인해야 합니다.

그래서 웹뷰의 이득은 만들 것이 많고 확인할 것은 적을 때 크다고 볼 수 있습니다. 총 공수의 차이가 크지 않더라도 사람의 능력은 저마다 다르기 때문에 더 얻는 이득이 있기도 합니다. 채용이 어려운 네이티브 앱 개발자 한 자리를 기존 웹 개발자의 추가 시간으로 바꾸는 것은 작은 조직에는 실질적인 이득으로 이어질 수 있습니다. 동시에 버스 팩터가 떨어지는 위험이기도 하지만 말이죠. 개발자와 회사의 입장이 갈리는 지점이라고도 할 수 있습니다.

하지만 여기서 이런 문제를 다루고자 하는 것은 아닙니다. 웹뷰로 간단한 채팅 UI를 모방하면서 제가 경험했던 기술적인 문제를 먼저 회고하고자 합니다.

## SafeArea 문제

SafeArea는 스마트폰 화면에서 상태바, 노치, 홈 인디케이터 등 시스템 요소에 앱 콘텐츠가 가려지지 않도록 배치된 여백을 의미합니다. Flutter에서는 기본 제공되는 SafeArea 위젯을 통해 이를 확보할 수 있습니다. 덕분에 시스템 요소는 콘텐츠를 가리지 않습니다. 다만 디자인 요구사항에 따라 SafeArea를 건드려야 할 때가 있습니다. 혹은 SafeArea가 없어야 하는 화면이 필요할 수도 있습니다. 결국 웹뷰에서 이런 요구사항에 유연하게 대처하기 위해서는 네이티브에서 SafeArea 설정을 꺼야 합니다. 그렇다면 앱 콘텐츠가 SafeArea에 가려지는 문제는 어떻게 해결해야 할까요?

결론부터 말하자면, 웹이 그 책임을 가져가야 합니다. 브릿지를 통해 웹으로 SafeArea의 높이를 전송하고 웹은 이 정보를 받아 필요에 따라 여백을 확보하거나, 무시합니다. 그렇다면 웹이 SafeArea를 알아야 합니다.

Flutter에서 제공하는 [FlutterView](https://api.flutter.dev/flutter/dart-ui/FlutterView-class.html)는 Flutter 엔진 안에서 하나의 화면 출력 영역을 나타냅니다. 이 객체는 여러 메트릭 정보를 제공하며 주요 정보는 다음과 같습니다.

- physicalSize: 화면 영역의 실제 pixel 크기
- devicePixelRatio: 논리적 픽셀 대비 물리적 픽셀 비율
- viewPadding: 노치,  상태바 등으로 가려질 수 있는 고정 영역
- viewInsets: 키보드처럼 현재 콘텐츠를 완전히 가리는 영역
- padding: viewPadding과 viewInsets를 조합해 계산된 현재 사용 가능한 안전 여백

여기서 SafeArea는 padding이라고 볼 수 있습니다. padding은 viewPadding과 viewInsets의 조합으로 계산되는데, 그 공식은 다음과 같습니다

```dart
padding = max(0, viewPadding - viewInsets)
```

하나의 예를 들자면, 키보드가 열리기 전, 다시 말해 viewInsets가 0인 상황에서는 하단 시스템 네비게이션 바의 높이가 padding이 됩니다. 반대로 키보드가 열리면, 즉 viewInsets가 시스템 네비게이션 바의 높이를 넘는 상황에서 padding은 0입니다. padding을 통해 상하좌우의 여백을 모두 얻을 수 있는데, 보통 top과 bottom만으로 충분합니다.

FlutterView에서 제공하는 값들은 기본적으로 물리적 픽셀 단위입니다. 따라서 이 값을 그대로 넘기기 보다는 논리적 픽셀로 변환하여 보내는 것이 편합니다.

```dart
final safeAreaTop = view.padding.top / view.devicePixelRatio;
```

Flutter 위젯 안에서는 아래 코드로 논리적 픽셀 값을 바로 얻어낼 수도 있지만, 저의 경우에는 특정 위젯이 아닌 전역 WidgetBinding에 observer를 등록하는 방식을 사용하고 있어서 FlutterView 객체를 직접 다루고 있습니다.

```dart
final padding = MediaQuery.paddingOf(context);
```

웹에서는 브릿지를 통해 이 값을 구독하고 CSS 변수로 등록합니다.
```javascript
appBridge.state.subscribe({
  onNext(state) {
    if (state.safeArea) 
    }
  },
});
```

이제 레이아웃 컴포넌트에서는 필요에 따라 이 값을 사용하면 됩니다. 단 웹뷰 내에서 새로고침 되는 경우가 있다면, 브릿지가 다시 연결되는 과정에서 웹에서 설정한 여백이 순간 사라질 수 있으니 주의해야 합니다. 가급적 웹 페이지가 앱 사용 중에 새로고침되지 않도록 구현하는 것이 좋겠지만, 만약 그게 어렵다면 별도 보완책을 마련하는 것이 좋습니다.

## 키보드 문제

### 문제 현상과 원인

채팅 UI를 개발하면서 이런 문제를 만났습니다. 키보드가 올라올 때 화면이 버벅이는 모습이 보이시나요? 저는 이것을 단순하게 키보드 문제라고 부르겠습니다.

[gif:chat log jitter]
[caption:키보드가 나타나고 사라질 때, 화면이 버벅이는 모습이 보이시나요?]

화면에 그려지는 DOM 요소가 많아질 수록, 가령 수학 표기를 위한 MathML 요소가 많거나 대화 내역이 많은 경우에는 이 현상이 두드러지게 나타났습니다. 메세지가 많은 것은 react-virtuoso 같은 DOM 가상화 라이브러리를 통해 꽤나 해소할 수 있었지만, 하단에 배치된 Input이 떨리는 현상은 크게 개선되지 않았습니다.

이 현상을 겪었을 당시에는 화면이 상당히 무겁고 복잡한 구조를 갖고 있었습니다. 그래서 웹에서 이러한 부분들을 개선하면 문제가 해결될 것으로 기대했습니다. 그런데 모든 의심되는 요소를 걷어내며 실험을 해봤을 때 키보드가 오르내리면서 웹뷰 레이아웃의 사이즈가 바뀌는 것이 근본적인 원인이라는 사실이 드러났습니다.

대부분의 채팅 UI는 하단에 Input을 배치하고 있습니다. 사용자가 Input을 터치하고 키보드가 올라올 때 Input은 키보드 위에 배치됩니다. 웹뷰에서 이를 구현하기 위한 가장 단순한 방법은 키보드가 올라올 때 웹뷰 사이즈 자체를 줄이는 방법입니다. Flutter에서 최상위 컨테이너라고 할 수 있는 Scaffold에는 resizeToAvoidBottomInset이 true로 설정되어 있습니다. 이는 키보드가 올라온 만큼 위젯 크기를 줄인다는 것을 의미합니다. 따라서 별도의 명시적인 설정 없이도 웹뷰 사이즈를 줄이는 구현을 할 수 있습니다.

하지만 키보드의 나타남 여부에 따라 웹뷰 레이아웃이 줄어들고 늘어나는 것이 문제의 원인이기 때문에 이젠 이 방법을 채택할 수 없습니다.

### 리사이즈 책임을 웹으로

웹뷰 레이아웃이 바뀌는 것이 문제의 원인이라는 사실을 알게 되었으니 키보드에 따라 사이즈가 바뀌지 않도록 하는 것은 어떨까요? resizeToAvoidBottomInset 속성을 끄면 되겠죠? 이제는 네이티브에서 화면을 줄여주지 않기 때문에 그 책임을 웹이 가져가야 합니다.

웹은 키보드 높이를 알아야 합니다. 키보드 높이에 따라, 필요시 내부 DOM 요소를 줄이거나 늘릴 겁니다. 앞서 언급한 FlutterView 객체의 viewInsets 속성에서 필요한 값을 얻을 수 있습니다. 이걸 logical pixel로 변환하고 이를 브릿지를 통해 웹에 전달합니다. 웹은 SafeArea 값에 따라 여백을 확보했던 것처럼 이 높이를 사용하여 웹 콘텐츠의 사이즈를 조절합니다.

웹뷰 레이아웃 사이즈가 통째로 바뀌는 것은 막았지만, 결국 이 방법도 내부적으로 DOM 사이즈를 바꿉니다. 그에 따라 Reflow가 발생하니까 이 값을 갱신할 때는 requestAnimationFrame을 사용하는 것이 좋습니다. 경우에 따라 debounce 등도 고려하는 것도 좋은 방법일 것 같습니다.

(근데 뭔가 raf 써도 버벅일 때가 있었다. 왜일까?)

### 또다른  문제

"이제 잘 되겠지"라고 생각하던 중 또다른 문제를 발견했습니다. 키보드가 나타나 있을 때 웹뷰 내에 있는 fixed 요소를 잡고 위로 당기면 뷰포트에 위치한 UI가 통째로 화면 밖으로 밀려나는 현상이 있었습니다. 개발자 도구로 HTML 요소의 크기를 확인했을 때 사이즈 자체에는 문제가 없었습니다.

[image:html size debugging]

근데 실제로 DOM 요소가 화면을 벗어나고 있었어요. 결국 HTML 밖에서 벌어지는 일이라는 건데 이미 Flutter에서 할 수 있는 것들을 다 했다고 생각하고 있었기에 막막함을 느꼈습니다.

그러던 중 flutter_inappwebview에서 수직 스크롤 차단을 허용하는 disableVerticalScroll를 발견했습니다. HTML과 무관하게 웹뷰 자체가 스크롤을 가질 수 있다는건가 싶은거죠. let startedByUser =
    scrollView.isDragging || scrollView.isDecelerating
if startedByUser {

scrollView의 상태에 따라 사용자 제스처에 의한 스크롤을 구분하는 것을 볼 수 있습니다. 사용자 제스처에 따라 스크롤하는 것만 막는 것도요. 따라서 iOS에서는 뷰포트가 밀리는 동작이 여전히 발생할 수 있습니다. 그렇다면 이 문제를 방지하기 위한 몽키 패치도 필요할까요? 그게 더 근본적인 해결책일 수도 있겠지만, 저는 기본 지식이 부족한 상태에서 위험한 변경은 최소한으로 기하고자 했습니다.

따라서 `pointerdown` 이벤트 핸들러를 붙이고 이벤트의 기본 동작을 차단하는 방법을 택했습니다. 코드는 대략 다음과 같습니다.

```tsx
const handlePointerDown = (
  event: React.PointerEvent<HTMLInputElement | HTMLTextAreaElement>,
) => {
  const input = event.currentTarget;
  
  // 이미 포커스된 요소라면 리턴
  if (document.activeElement === input) return;

  // pointerdown 기본 동작 취소
  event.preventDefault();
  
  // 직접 focus 호출
  input.focus({ preventScroll: true });
};

<textarea onPointerDown={handlePointerDown} />
```

다만 이 방법은 완벽하진 않을 수 있습니다. 실제로 이 코드를 반영한 이후에도 간혹가다 문제 현상을 목격한 적이 있었던 것 같습니다. 이렇게 모호하게 말씀드린 이유는 그 시점이 정확하지 않기 때문인데 나중에 다시 목격하게 된다면 글을 수정하겠습니다. 그래도 거의 해결된 것으로 보입니다...!

### 근데 모바일 브라우저에서는?

모바일 브라우저까지 고려하지 않아도 된다면 이 절은 건너 뛰셔도 됩니다. 하지만 제가 만드는 제품은 모바일 브라우저까지 지원해야 했습니다. 키보드가 올라올 때 사이즈를 줄이는 요구사항, fixed 요소를 잡고 올렸을 때, 키보드가 나타날 때 뷰포트가 밀리는 문제는 여전히 남아있습니다. 웹뷰 설정은 당연히 모바일 브라우저에 영향을 줄 수 없으니 웹 코드에서만 이 문제를 방지해야 합니다.

먼저 사이즈 문제부터 해결해보겠습니다. Viewport meta tag는 뷰포트의 크기와 모양을 제어할 수 있는 방법을 제공합니다. 채팅 UI에서는 소프트 키보드가 뷰포트에 영향을 줄 수 있으니, 브라우저가 크기를 조정할 수 있는 수단을 제공합니다. 다음과 같이 소프트 키보드가 올라올 때 레이아웃 뷰포트 사이즈를 줄이도록 합니다.

```html
<meta name="viewport" content="interactive-widget=resizes-content" />
```

하지만 아쉽게도 이건 반쪽자리 해결책입니다. iOS 사파리에서는 지원하지 않는 기능이기 때문이죠. 그래서 다른 방법을 생각해야 합니다.  모바일 브라우저에 키보드가 열려도 layout viewport인 window.innerHeight는 대체로 유지됩니다. 그리고 실제 보이는 영역인 visualViewport.height가 줄어듭니다. 이 점을 이용합니다.

```
Layout viewport
┌─────────────────┐
│                 │
│ Visual viewport │
│                 │
├─────────────────┤
│    Keyboard     │
└─────────────────┘
```

하단에 키보드에 의해 가려진 영역은 다음 공식으로 구합니다.
```javascript
const insetBottom = Math.max(
  0,
  window.innerHeight - visualViewport.height - visualViewport.offsetTop,
);
```

offsetTop을 빼는 이유는 포커스로 인해 visualViewport가 이동한 값을 키보드 높이로 잘못 계산하지 않기 위해서입니다. 이제 이 값을 웹뷰에서와 같이 CSS 변수로 등록하여 사용하면 됩니다. 일관성을 위해 Viewport meta tag를 사용하지 않고 이 방식만 적용하는 것도 가능하겠지만, 안드로이드의 경우 Viewport meta tag를 사용하는 것이 더 안정적이기 때문에 둘다 반영하는 것을 권장합니다.

이제 스크롤 문제가 남았습니다. 이건 다소 단순하고 무식한 방법밖에 찾지 못했습니다. 실제 브라우저의 동작을 바꿀 수 없기 때문입니다. 키보드가 열리면 스크롤 이벤트 리스너를 붙이고 스크롤을 잠급니다.

```tsx
const lockRootScroll = () => {
  const root = document.documentElement;
  const previousOverflow = root.style.overflow;

  const resetScroll = () => {
    if (window.scrollY !== 0) {
      window.scrollTo(0, 0);
    }
  };

  root.style.overflow = "hidden";
  resetScroll();
  window.addEventListener("scroll", resetScroll);

  return () => {
    root.style.overflow = previousOverflow;
    window.removeEventListener("scroll", resetScroll);
  };
};

```

이 방식의 한계는 결국 이벤트가 먼저 발생한 이후 스크롤을 고정하기 때문에 shift 현상이 남는다는 점입니다. 따라서 안드로이드에서는 Viewport meta tag 설정을 유지하여 스크롤 문제를 원천적으로 차단하고, iOS를 위한 미봉책으로만 적용하는 것이 좋습니다. (fixed 관련하여 더 좋은 방법이 있을 수도?)
